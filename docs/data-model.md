# QuickNotes Data Model

This design uses PostgreSQL-style SQL types. UUIDs are generated by the application or a database UUID function. Timestamps are stored in UTC.

## Entities and relationships

| Entity | Columns | Primary key | Foreign keys |
|---|---|---|---|
| `users` | `id UUID NOT NULL`; `email VARCHAR(320) NOT NULL`; `password_hash TEXT NOT NULL`; `created_at TIMESTAMPTZ NOT NULL` | `id` | None |
| `notes` | `id UUID NOT NULL`; `owner_id UUID NOT NULL`; `title VARCHAR(100) NOT NULL`; `body TEXT NOT NULL`; `created_at TIMESTAMPTZ NOT NULL`; `updated_at TIMESTAMPTZ NOT NULL` | `id` | `owner_id` references `users(id)` |
| `tags` | `id UUID NOT NULL`; `owner_id UUID NOT NULL`; `name VARCHAR(50) NOT NULL`; `created_at TIMESTAMPTZ NOT NULL` | `id` | `owner_id` references `users(id)` |
| `note_tags` | `note_id UUID NOT NULL`; `tag_id UUID NOT NULL`; `owner_id UUID NOT NULL`; `created_at TIMESTAMPTZ NOT NULL` | Composite key: (`note_id`, `tag_id`) | (`note_id`, `owner_id`) references `notes(id, owner_id)`; (`tag_id`, `owner_id`) references `tags(id, owner_id)` |

A user has zero or more notes, and each note belongs to exactly one user: this is a **one-to-many** relationship from `users` to `notes`. A user also owns zero or more tags. Notes and tags have a **many-to-many** relationship: a note can have many tags, and a tag can be applied to many notes. `note_tags` is the junction table for that relationship. Its owner column and composite foreign keys ensure a note cannot be linked to another user's tag.

## Schema

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY,
    email VARCHAR(320) NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE notes (
    id UUID PRIMARY KEY,
    owner_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(100) NOT NULL,
    body TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (id, owner_id)
);

CREATE TABLE tags (
    id UUID PRIMARY KEY,
    owner_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name VARCHAR(50) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (owner_id, name),
    UNIQUE (id, owner_id)
);

CREATE TABLE note_tags (
    note_id UUID NOT NULL,
    tag_id UUID NOT NULL,
    owner_id UUID NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (note_id, tag_id),
    FOREIGN KEY (note_id, owner_id)
        REFERENCES notes(id, owner_id) ON DELETE CASCADE,
    FOREIGN KEY (tag_id, owner_id)
        REFERENCES tags(id, owner_id) ON DELETE CASCADE
);

CREATE INDEX idx_notes_owner_created
    ON notes(owner_id, created_at DESC, id);

CREATE INDEX idx_note_tags_tag
    ON note_tags(tag_id, note_id);
```

The `notes(owner_id, created_at DESC, id)` index supports a user's paginated note list in newest-first order without scanning other users' notes. The `note_tags(tag_id, note_id)` index supports finding notes by tag; the primary key already supports looking up tags for a note. Email and tag uniqueness constraints also create the indexes needed to enforce those rules.

## Example queries

List a user's notes newest first, using a stable cursor for pagination:

```sql
SELECT id, title, body, created_at, updated_at
FROM notes
WHERE owner_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT $4;
```

Retrieve the tags applied to a note (**JOIN**):

```sql
SELECT t.id, t.name
FROM note_tags AS nt
JOIN tags AS t
  ON t.id = nt.tag_id
 AND t.owner_id = nt.owner_id
WHERE nt.note_id = $1
  AND nt.owner_id = $2
ORDER BY t.name;
```

Find all notes for a user with a given tag name (**JOIN**):

```sql
SELECT n.id, n.title, n.body, n.created_at, n.updated_at
FROM notes AS n
JOIN note_tags AS nt
  ON nt.note_id = n.id
 AND nt.owner_id = n.owner_id
JOIN tags AS t
  ON t.id = nt.tag_id
 AND t.owner_id = nt.owner_id
WHERE n.owner_id = $1
  AND t.name = $2
ORDER BY n.created_at DESC, n.id DESC;
```

## SQL or NoSQL?

SQL is a good fit because QuickNotes has clear relationships among users, notes, and tags, and needs referential integrity so notes and tags cannot be orphaned or cross-linked between users. Transactions make note creation, updates, and tag assignments reliable, while indexes support user-scoped pagination and tag lookups. PostgreSQL can scale reads with replicas and keep the relational model as the product grows; a NoSQL store could be reconsidered if measured access patterns later require a different scaling model.
